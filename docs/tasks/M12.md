## Deliver `internal/runner`
- `Runner` drives one run through the statuses and phases in PLAN.md section 2. Every status/phase change goes
  through the store's compare-and-set update together with an event row.
- Modes `fix`, `refine` and `investigate` exactly as in the modes table. `refine` never codes.
- Refine: preflight (repo in config, issue readable, budget), read-only clone, refine stage, save the spec
  version and hash, post the spec or the questions on the issue, then `awaiting_approval` or `needs_info`.
  Delete the workspace while waiting.
- `Approve(runID, approver)`: only from `awaiting_approval`, only for the latest spec version and hash, then
  records the approval and moves to `approved`. `Revise(runID, notes)` reruns refine and enforces the
  5-revision limit. `Reject` closes the run without pushing anything. `Cancel` stops an active run
  (context cancel plus a CAS to `cancelled`).
- Code phase: start only from `approved`. Obtain the approval token from the agent gate (never construct
  one), re-clone at the spec's base SHA, create branch `patchbot/issue-<n>`, run baseline tests, run the code
  stage, have the harness run the tests (at most 3 attempts), then commit, push and open a PR. The PR is a
  draft when tests are not green. The PR body links the approved spec, ticks the claimed acceptance
  criteria next to the harness test result, and notes when the default branch has moved. Post an issue
  comment with the PR link.
- `--dry-run`: run everything up to publish, then print the spec, diff and PR text. Push nothing and post
  nothing to GitHub.
- GitHub `/approve` and `/revise <notes>` comments count only for runs that are waiting. The author must be
  in `approvers` and be a repo collaborator. Edited comments never count. Implement this as a single sync
  pass, `SyncWaiting(ctx)`, that `serve` (M13) will call every 60 s and `patchbot runs --sync` calls once.
- Expiry: waiting runs older than 14 days become `failed` with error kind `expired`.
- `FailStaleRuns` on start-up, crash-safe heartbeats, and one budget for the whole run including revisions,
  capped by `hard_max_cost_usd`.
- Retry: a new run linked by `retry_of`, with optional provider and model. Reuse the approved spec only if
  the issue is unchanged (same issue hash).

## CLI (`internal/cli`)
`patchbot run --repo owner/name --issue N [--mode fix|refine|investigate] [--provider P --model M]
[--dry-run]`, `approve <id>`, `revise <id> --notes "..."`, `reject <id>`, `cancel <id>`,
`runs [--status S] [--sync]`, `retry <id> [--provider P --model M]`. CLI approvals are recorded under the
configured local approver name. There is no pre-approve flag. Exit codes and messages must be clear. Never
print secrets.
