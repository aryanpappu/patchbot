## M5b: remaining tools (internal/tools)
- run_cmd: argument {name, args?}. Resolves through execx.Policy (named commands only), runs via an injected
  execx.Executor in the workspace dir with MinimalEnv (private HOME/TMP under the run dir), returns exit code, timed-out
  flag and capped, redacted output (8 KB to the model; full capped output kept for the step record). Only in the code registry.
- submit (code stage): {summary, pr_title, pr_body?, criteria: [{text, met: bool, note?}]}.
- submit_spec (refine stage): {summary, acceptance_criteria[], files[], risks[], test_plan[], open_questions[]}. If
  open_questions is non-empty the spec is "needs_info". Renders deterministic markdown + sha256 hash of the canonical form.
- submit_report (investigate): {report_md}.
- Terminal tools end the loop; the registry exposes which tool names are terminal.

## M6: internal/agent
- Loop.Run(ctx, Session, Limits) (Outcome, error) exactly as PLAN-fable 4.3: cancel, deadline, max turns, budget
  pre-check with worst-case reservation (llm pricing Reserve), compaction at 70% of the context window (replace old tool
  outputs with a stub, keep call/result pairs valid), call provider, account usage/cost (unknown usage keeps the
  reservation and marks accounting uncertain), append assistant message, dispatch tool calls sequentially in order, one
  tool message with all results, terminal tool -> end. End-turn without tool calls: nudge once, then synthesize. Max
  tokens: drop truncated calls, nudge. Refusal -> EndRefusal. Stuck detector (same name+args hash 3x -> warn, again -> EndStuck).
  Error kinds per PLAN-fable 4.4 (auth no retry, context_too_long force-compact once, etc). Every LLM call and tool call is
  recorded through a small Recorder interface (implemented by an adapter over store.Store + an event emitter interface)
  and redacted before recording.
- Stage engines on top of Loop:
  - Refine(ctx, req) -> SpecResult | Questions: read-only registry + submit_spec, refine prompt with the issue as
    untrusted data, optional revise notes and prior spec version.
  - Code(ctx, req) -> CodeResult: requires an ApprovalToken obtained only from gate.Check (below); code registry + run_cmd
    + submit; then the harness test-retry loop of PLAN-fable 4.5 (harness runs the repo's configured test command via
    execx, never trusts the model; failing output head 2 KB + tail 6 KB fed back; max_test_attempts; turns/budget carry over),
    and the salvage rule (4.6) as an outcome flag for the runner.
  - Investigate(ctx, req) -> ReportResult: read-only registry + submit_report.
- internal/agent/gate (or a gate.go): Check(ctx, store, runID, issueHash) returns an unexported-constructor
  ApprovalToken only when: run status is approved, latest spec exists, store.ValidApproval matches its version and hash,
  the spec's issue_hash equals the current issue hash, the approval is not older than the configured TTL, and revisions
  <= max. Code() refuses without a token, and the code registry (write tools) is only built after the token check. This
  is hard rule 1 of the product: make it impossible to call Code without passing the gate (unexported token type).
- prompts.go: original system prompts for refine, code and investigate (embed as text files). Issue title/body, repo
  files, and test output are wrapped as clearly delimited untrusted data; the prompt states limits are enforced outside
  the model. No copied text from any other project.
